# Инварианты CAOS

Статус: черновик для ревью (Track B плана улучшения).
Назначение: «конституция» системы — правила, которые backend **физически не позволяет нарушить**, а не правила, которые написаны в документации. Каждый инвариант сопровождается способом проверки (тестом).

Обозначения статуса: ✅ enforced — уже гарантируется кодом; 🔶 partial — частично; ⬜ planned — внедряется в соответствующем треке плана (C/E/G/H).

---

### INV-1. Цель не становится коллективной без процедуры признания

Формулировка: объект `Goal` в статусе `accepted/active` может существовать только после прохождения процедуры (proposal → обсуждение → признание). Никакой единоличный `POST /goals` не создаёт принятую цель.

Почему: защита одновременно от иерархии («начальник назначил») и атомизации («каждый создал свою цель»).

Проверка: тест — попытка создать цель сразу в статусе `active` отклоняется; переход `draft → proposed → accepted` возможен только командами с проверкой прав.

Статус: ⬜ (C2). Сегодня цель создаётся сразу и не имеет жизненного цикла вообще.

---

### INV-2. Не существует «бесхозной» деятельности

Формулировка: каждая Activity/Task связана с целью напрямую или через Commitment. Система всегда может ответить, какой цели служит любая единица работы.

Проверка: тест — создание задачи без связи с целью/обязательством отклоняется; аудиторский запрос «задачи без цели» возвращает пусто.

Статус: ⬜ (C4). Сегодня Task связан только с проектом, а проект может не иметь цели.

---

### INV-3. Выполнение задачи ≠ достижение цели

Формулировка: `task.status = done` не изменяет статус цели и не создаёт результата. Переход цели к `achieved` возможен только через Result + Verification.

Проверка: тест — завершение всех задач цели не меняет её статус; `achieved` требует проверенный Result.

Статус: ⬜ (C5). Сегодня статусы задач и целей никак не связаны (что хотя бы не создаёт ложных переходов).

---

### INV-4. Результат не считается проверенным по факту сообщения исполнителя

Формулировка: `Result.status = verified` устанавливает верификатор, отличный от автора результата; verification требует Evidence.

Проверка: тест — исполнитель не может верифицировать свой результат; верификация без evidence отклоняется.

Статус: ⬜ (C5). Сегодня сущности Result нет.

---

### INV-5. AI не изменяет доменное состояние напрямую

Формулировка: единственный путь влияния AI — создать AIProposal со статусом `under_review`, который человек принимает/отклоняет/правит. В коде нет функции «AI пишет в таблицы целей/решений/результатов».

Почему: доверие к коллективным данным; «AI помогает, но не управляет».

Проверка: тест — ни один AI-эндпоинт не производит мутаций доменных таблиц; accepted AIProposal порождает изменение только от имени пользователя-ревьюера.

Статус: ✅ enforced de facto (AI сегодня только читает и советует), формализуется в G1.

---

### INV-6. Заблокированное по безопасности предложение не порождает деятельность

Формулировка: GoalProposal в статусе `blocked/flagged` не может создать Goal, Commitment, Task или попасть в поиск/рекомендации/AI-контекст.

Проверка: тест — попытка создать обязательство на основе заблокированного предложения отклоняется.

Статус: ⬜ (H2). Safety-слоя пока нет.

---

### INV-7. Делегирование имеет границы и срок

Формулировка: любое делегированное полномочие содержит `scope` (на что именно) и `valid_until`; по истечении срока полномочие прекращается автоматически; отзыв быстрее выдачи.

Проверка: тест — действие по истёкшему делегированию отклоняется; cover: отзыв меняет доступ немедленно.

Статус: ⬜ (H1).

---

### INV-8. История значимых объектов не удаляется

Формулировка: для целей, решений, результатов, обязательств запрещён физический DELETE — только смены состояний (`abandoned`, `superseded`, `withdrawn`). Аудит append-only.

Почему: «память организации» — без истории невозможно ответить «почему мы решили X?».

Проверка: тест — DELETE-эндпоинты отсутствуют; смена состояния сохраняет предыдущую запись; удаление пользователя анонимизирует вклад, а не уничтожает.

Статус: 🔶 partial — аудит-трейл пишется (`AuditEvent`), сущности не удаляются через API, но смена статусов свободная и анонимизация частичная.

---

### INV-9. Доступ проверяется отдельно от существования

Формулировка: `404` — объект не существует; `403` — существует, но недоступен. Ни один список/поиск/AI-ретривал не раскрывает объекты вне права доступа пользователя; ссылка на объект в другом объекте требует права на оба.

Проверка: тесты Track A (A4/A7) уже гоняют эти сценарии; регулярное добавление кейсов «двух пользователей» для каждого нового эндпоинта.

Статус: 🔶 partial — закрыты основные CRUD/AI-пути (коммит c15c147), матрица прав `Can(user, action, object)` — D1.

---

### INV-10. Взгляды участника — не основание для ограничения доступа

Формулировка: политическая/идеологическая позиция пользователя никогда не является критерием блокировки; ограничения касаются действий и содержания («допустимое действие / недопустимое действие»), а не «агент/не агент». Нет политических скорингов, нет рейтингов людей.

Проверка: ревью любых модерирующих механизмов на соответствие; запрет полей вида `loyalty_score`, `provocation_probability` в схеме БД.

Статус: ⬜ (H2, фиксируется ревью-практикой).

---

## Дополнительные структурные инварианты (C1)

### INV-11. Граф целей не содержит запрещённых циклов

Циклы по комбинации `depends_on` + `concretizes` отклоняются при создании ребра. Тест: property-based прогон на случайных графах.

### INV-12. Приоритет цели не сводится к одному глобальному числу

Приоритет контекстен (значимость/срочность/зависимость/ресурсы относительно субъекта и срока); глобальный числовой рейтинг целей и любые KPI людей запрещены (документируется здесь, проверяется ревью).

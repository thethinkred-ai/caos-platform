# Онтология CAOS 0.2

Статус: черновик для ревью (Track B плана улучшения `docs/plan-caos-0.2.md`).
Назначение: зафиксировать определения сущностей ДО их появления в коде. Каждый PR, меняющий доменную модель, ссылается на этот документ.

Центральный цикл CAOS:

```
ПОЛОЖЕНИЕ ДЕЛ → ПРОБЛЕМА → ЦЕЛЬ (через процедуру признания) → РЕШЕНИЕ →
УЧАСТИЕ → ОБЯЗАТЕЛЬСТВО → ДЕЯТЕЛЬНОСТЬ → РЕЗУЛЬТАТ → ДОКАЗАТЕЛЬСТВО →
ПРОВЕРКА → ОЦЕНКА → НОВОЕ ПОЛОЖЕНИЕ ДЕЛ
```

Ключевое различение, которого нет в таск-трекерах: **выполненная задача ≠ достигнутый результат ≠ решённая проблема**.

---

## 1. Situation (положение дел)

Описание существующего состояния дел, из которого вырастает проблема: факты, измерения, наблюдения. Не является «объектом для работы» — это основание для формулировки проблемы. В модели 0.2 — первая версия может жить внутри Problem (поля current_state / evidence), выделение в отдельную сущность отложено.

## 2. Problem (проблема)

Осознанное противоречие в положении дел, требующее изменения. Отвечает на вопросы: что происходит? почему это плохо? для какой деятельности? какие факты это подтверждают?

- Наследует текущую сущность `Problem`; дополняется полями: `situation` (факты), `scope` (чья деятельность затронута).
- Проблема — **основание цели, а не входная дверь системы**: пользователь может начать и с формулировки цели (тогда CAOS спросит «какое положение дел требует изменения?»).
- Не каждая проблема обязана стать целью (квалификация: proposed → qualified / rejected / deferred).

## 3. Goal (цель)

Коллективно признанное описание **желаемого изменения положения дел**, имеющее основание в проблеме, критерии проверки, границы и связи с другими целями.

- Цель ≠ задача и ≠ желание: «создать сайт» — задача; «обеспечить 100 участникам возможность самостоятельно находить цели» — цель.
- Поля: `current_state`, `target_state`, `success_criteria`, `scope`, `deadline`, `constraints` (что нельзя делать ради достижения).
- **Жизненный цикл**: `draft → proposed → under_review → accepted → active → achieved → verified → closed`; боковые выходы: `rejected`, `suspended`, `abandoned`, `superseded`. Переходы выполняются только серверными командами, произвольная смена статуса запрещена.
- Субъекты различаются: proposer (автор предложения) ≠ owner (держатель) ≠ participants (участники).
- Существующая таблица `goals` остаётся, эволюционирует полями.

## 4. GoalRelation (отношение целей)

Типизированное ребро графа целей. Именно оно делает CAOS графом, а не деревом.

- Типы (начальный набор): `concretizes`, `depends_on`, `supports`, `conflicts_with`, `contributes_to`, `blocks`, `supersedes`.
- Обязательное поле `rationale` — почему связь существует.
- `parent_goal_id` сохраняется как сахар над `concretizes`.
- Запрещённые циклы (например, по `depends_on` + `concretizes`) отклоняются на уровне БД/API.

## 5. Participation (участие)

Отношение человека к конкретной цели: `user, goal, role, status, visibility, joined_at, left_at`.

- Роли контекстные (в цели A — contributor, в цели B — reviewer): `contributor`, `coordinator`, `expert`, `facilitator`, `observer`.
- Заменяет собой членство в проекте/команде как основную форму связи человека с деятельностью (см. ADR-0004).
- Участие ≠ обязательство: можно следить за целью, не беря работы.

## 6. Commitment (обязательство)

Добровольно принятое обязательство внести конкретный вклад в цель: «я готовлю 3 урока до 1 октября».

- Поля: `user, goal, description, expected_result, success_criteria, deadline, source, status`.
- `source ∈ {self, decision, delegation}` — основание: собственная инициатива, коллективное решение или делегирование.
- Задача (Task) привязывается к цели через обязательство → «бесхозной» деятельности не существует (Инвариант 2).
- Отличие от поручения: не «начальник назначил», а «участник принял» (или цель приняла через решение).

## 7. Decision (решение)

Коллективно принятое решение об изменении (цели, способа действий, правил). Решение — **процесс**, а не голосование.

- Процесс: `Proposal → обсуждение (аргументы/возражения/альтернативы) → уточнение → принятие → исполнение → оценка`.
- `ProposalVersion` — версии предложения (что именно обсуждали и приняли).
- Методы: `majority`, `unanimity`, `consent`, `delegated` — метод обязан соответствовать подсчёту (сегодняшний «consensus» простым большинством — устранён).
- Решение имеет срок жизни: `valid_until`, `review_at`.
- Ссылается на изменяемый объект: `target_type, target_id` — «что именно решаем».
- Существующие `Decision`, `DecisionEvent`, `Vote` остаются как основа.

## 8. Activity (деятельность)

Осуществляемая работа: task, meeting, research, discussion. Подтипы различаются — не всё сводится к чекбоксу.

- Каждая деятельность связана с целью или обязательством (Инвариант 2).
- `Task` остаётся операционной единицей внутри Activity.
- Статус задачи: `todo / in_progress / done / cancelled` — и **done ≠ достигнута цель** (Инвариант 3).

## 9. Result (результат)

Изменение положения дел, достигнутое деятельностью: «доля завершивших курс выросла с 61% до 78%», а не «разработали интерфейс».

- Поля: `goal, activity, description, expected_state, actual_state, status, reported_by`.
- Статусы: `reported → under_verification → verified / partially_verified / rejected / disputed`. **reported ≠ verified** (Инвариант 4).
- Верификатор ≠ исполнитель.
- Для оценки хранится тройка baseline / target / actual.

## 10. Evidence (доказательство)

Объективное подтверждение результата: документ, измерение, метрика системы, внешняя ссылка, коллективная оценка.

- Привязывается к конкретному утверждению внутри результата, иначе это «декоративное вложение файла».
- Типы: `document, data, measurement, observation, external_source, system_metric, collective_assessment`.

## 11. Knowledge (знание)

Выработанный системой опыт, связанный с целями, решениями, результатами.

- Знание ссылается на источник: `Problem → Goal → Decision → Result → Evaluation → Knowledge` — отвечает на вопрос «откуда появилось это знание?».
- Ошибка — тоже знание: проваленная предпосылка сохраняется как опыт.
- Существующая `KnowledgeItem` остаётся, обрастает связями `KnowledgeRelation` (C7).

## 12. Challenge (возражение)

Структурированное оспаривание существенного объекта: цели, решения, результата.

- Поля: `target_type, target_id, author, claim, argument, evidence, alternative, status, resolution`.
- Возражение нельзя потерять: статусы `open → acknowledged → addressed / accepted / rejected / withdrawn / deferred`, при отклонении — обязательный ответ.
- Может стать центральным механизмом коллективного целеполагания: предложили → обосновали → оспорили → уточнили → приняли.

## 13. AIProposal (предложение AI)

Единственная форма, в которой AI влияет на систему: анализ + предложение, reviewable человеком.

- Поля: `model, model_version, target_type, target_id, proposal_type, input_snapshot, proposed_change, rationale, evidence, confidence, status, reviewed_by, reviewed_at`.
- Статусы: `generated → under_review → accepted / rejected / expired / modified`.
- **AI никогда не изменяет доменные объекты напрямую** (Инвариант 5, ADR-0003).
- Существующая `AISuggestion` эволюционирует в AIProposal (Track G).

---

## Что НЕ входит в онтологию

- **Project** — инструмент реализации, вторичен: связывается с целями многие-ко-многим (`ProjectGoal`), не является контейнером людей.
- **Team / TeamMember** — заморожены (не развиваются; людей связывает с деятельностью участие в целях).
- **Competence** — профильный атрибут участника, связывается с целями через требования Activity (C4), видимость ограничена.
- «Диалектические» названия в API/таблицах не используются — только инженерные имена (ADR-0002).

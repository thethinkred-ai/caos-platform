# Модель доверия: кто что видит в CAOS

Основание: вопрос владельца (18.10.2026): *«я как главный модератор буду видеть всё, что происходит в системе — значит, "недоверие учтено архитектурой" — неправда»*. Вопрос справедлив; этот документ — точный ответ, без округлений.

## Три уровня доступа

| Уровень | Кто | Что видит |
|---|---|---|
| **Приложение** | любой залогиненный пользователь | только свои объекты + цели, к которым у него есть доступ (владение / участие / членство в связанном проекте / активное делегирование) |
| **Контекст цели** | участники цели | всё внутри цели: обоснование, граф, обязательства, результаты, возражения |
| **Инфраструктура** | оператор сервера (root VPS, доступ к БД) | **всё**: закрытые цели любых пользователей, все голосования с именами авторов (таблица `votes` хранит `decision_id + user_id` открытым текстом), уведомления, сессии, журнал |

## Что это означает честно

1. **Роли «главный модератор» в приложении нет.** Поле `users.role` существует, но не используется ни одной проверкой доступа; администраторских эндпоинтов («посмотреть любую цель», «прочитать чужие сообщения») в API нет и не планируется. Ваша власть как пользователя — только над своими целями (владение/координация по матрице прав).
2. **Но оператор сервера технически видит всё.** Это неустранимо в данной архитектуре: ядро CAOS — серверные процедуры (чужая верификация результата, коллективное признание цели, инварианты). Сервер обязан обрабатывать данные, чтобы применять правила. Сквозное шифрование сделало бы невозможной главную функцию — сервер не смог бы проверить, что автор результата не верифицирует сам себя.
3. **Анонимность голосований — только на уровне API**: до финализации решения интерфейс показывает агрегаты, список с именами виден автору решения после итога. В базе голоса идентифицируемы.
4. **Что защищает от оператора на самом деле:**
   - открытый код (MIT) — можно проверить, что нет телеметрии, скрытых выгрузок, бэкдоров; прод публикует именно этот код;
   - экспорт (профиль и цель целиком в Markdown) — данные не в заложниках, участники могут уехать;
   - append-only аудит в приложении — действия через API оставляют след (но прямой доступ к БД этот след обходит, см. п. 5);
   - **главное: недоверенный коллектив может развернуть свой инстанс** — ответ на «внешнюю систему» не в обещаниях оператора, а в том, что систему можно сделать внутренней. Для вашего сообщества на вашем сервере оператор — вы; для чужого коллектива — они сами.
5. **Чего защиты нет** (дорожная карта): оператор с доступом к БД может не только читать, но и незаметно изменять данные в обход аудита. Противоядия из критики (Шаг 20–21), реализуемые по мере роста: псевдонимизация голосов в БД (HMAC вместо `user_id`), хэширование refresh-токенов, разделение оператора и аудитора, «два ключа» на операции с БД, внешние подписи событий (tamper-evidence).

## Как это подавать сообществу

Формула честности: **«CAOS не обещает, что оператор ничего не видит. CAOS гарантирует, что оператора можно не выбирать из чужих: код открыт, данные экспортируемы, инстанс разворачивается свой. Внутри приложения никто — включая оператора через API — не имеет прав модератора содержимого».**
